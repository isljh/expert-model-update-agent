# 最小模型更新智能体产品规格

## 文档状态

- **状态：** 第一版设计基线
- **适用范围：** 首个由人类编排的端到端模型更新原型
- **不代表：** 已选择首个验证项目、已经实现 EWC、已经确定最终接口格式或自动编排框架

## 1. 产品定义

最小模型更新智能体接收一个由人类明确创建的模型更新任务，通过相互隔离的决策、执行和审阅角色，完成策略规划、真实项目适配、小规模验证、正式训练、评估和独立验收，最终交付可加载的新模型权重及完整证据。

第一版验证的是“可追溯的模型更新闭环”，而不是方法数量、自动发现更新需求或无人值守大规模训练。

## 2. 用户与核心需求

主要用户是能够定义模型目标、数据边界、资源限制和验收标准的项目负责人。用户需要：

1. 在高成本训练前理解并批准更新策略。
2. 确认执行 Agent 在真实项目中验证了方法前提，而不是机械套用方案。
3. 获得实际训练产生、可加载且可追溯的新权重。
4. 用对应正确数据与 checkpoint 的指标比较原模型和新模型。
5. 由独立角色核验交付证据、偏差和剩余风险。

## 3. 范围

### 3.1 第一版包含

- 人类显式创建“需要更新”的任务。
- 一种经计划选定的增量学习方法；EWC 是首个案例候选，但须经任务计划确认。
- 一个规模较小、训练可重复的 PyTorch 目标项目。
- 决策、执行、审阅三个独立 Agent Session。
- 人工计划批准、正式训练批准和最终交付批准。
- 失败后的重新规划、修复后重试或终止。
- 权重、配置、日志、指标、代码差异、模型档案和审阅记录的关联交付。

### 3.2 第一版不包含

- 自动判断模型是否需要更新。
- 同时支持或自动比较大量增量学习方法。
- 无人值守的高成本训练和资源调度。
- 固定绑定 LangGraph、A2A、MCP、数据库或云平台。
- 对任意模型项目进行无条件一键改造。
- 用 Agent 自述代替命令结果、权重加载和独立审阅。

## 4. 最小成功条件

一次任务只有同时满足以下条件，才能进入“可交付”：

1. 已批准的 `UpdatePlan` 与实际执行可相互追溯。
2. 原模型和原权重未被覆盖或污染。
3. 执行 Agent 完成小规模验证，并在单独批准后完成正式训练。
4. 新权重存在，具有完整性校验信息，并在约定环境中成功加载。
5. 原模型与新模型指标注明数据、评估配置和 checkpoint，满足已批准的验收规则。
6. 代码版本、配置、真实命令、退出状态、日志、权重和指标关联到唯一运行编号。
7. 独立审阅 Agent 检查原始证据并给出明确结论。
8. 人类批准最终交付；已知风险和限制没有被隐藏。

仅修改代码、仅生成权重、仅报告指标或仅由执行 Agent 声明成功，均不满足完成条件。

## 5. 角色、权限与禁止事项

工具权限描述的是最小能力集合，不指定具体工具协议或产品实现。

| 角色 | 核心职责 | 最小工具权限 | 禁止事项 | 主要输出 |
| --- | --- | --- | --- | --- |
| 更新决策 Agent | 解释目标；分析模型与约束；选择更新方法；列出前提、风险、保留目标和验收要求；在收到证据后重新规划 | 只读任务材料；模型元数据与结构分析；方法知识；只写计划与决策记录 | 修改目标项目；启动训练；猜测具体文件、行号、数据入口或 loss 位置；把候选方法写成永久选择 | `UpdatePlan` |
| 更新执行 Agent | 读取已批准计划；理解目标项目；核实计划前提；定位真实数据、模型、训练和评估路径；修改代码；运行验证、训练和评估；保存证据 | 隔离工作区读写；受控命令执行；允许范围内的数据与模型读取；训练与评估；日志和产物写入；资源观测 | 覆盖原模型；越过数据与修改边界；在前提不成立时强行实施；自行放宽验收标准；把未运行或失败的步骤标为成功；自批正式训练或最终交付 | `ExecutionResult` 或带证据的重规划请求 |
| 独立审阅 Agent | 独立核对计划、代码差异、命令与退出状态、配置、日志、权重、加载验证和指标归属；检查验收条件 | 对任务、计划、工作区和产物的只读访问；可运行受控的非破坏性复验；只写审阅记录 | 修改实现或训练结果；替执行 Agent 补造证据；仅依据执行总结通过；改变计划或验收标准；批准最终交付 | `ReviewResult` |

人类负责创建任务、定义边界与验收标准、批准计划、批准高成本正式训练、处理超范围请求，并作最终交付决定。人类不需要逐文件指导实施。

## 6. 最小逻辑契约

本节定义字段语义，不决定采用 JSON、YAML、数据库或 API。所有契约都必须可版本化、可校验，并能够引用外部大文件而不把其内容嵌入 Agent 上下文。

### 6.1 通用信封

四类契约至少共享以下追溯语义；具体字段位置由各自的机器 Schema 确定：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 契约结构版本 |
| `task_id` | 模型更新任务的稳定唯一标识 |
| 契约实例版本 | 同一任务中该契约的修订版本，重规划或修改不得静默覆盖 |
| 创建与确认信息 | 能够识别确认主体并绑定适用版本；角色、时间等审计元数据按具体契约需要定义 |
| 契约状态 | 当前契约自身的状态，而非任务状态的替代品 |
| 稳定引用 | 对上游契约、代码版本、运行记录和证据的显式引用 |

引用必须能定位到稳定路径、内容摘要或受管理的外部标识。大日志、数据和权重只保存引用与完整性信息。

### 6.2 `TaskInput`：任务输入契约

`TaskInput` v0.2 只保留任务确认所需的最小内容：

| 分组 | 最小内容 |
| --- | --- |
| 标识与版本 | `schema_version`、`task_id`、`task_input_version` |
| `request` | 原始 Prompt，以及经整理、待确认或已确认的更新目标和原因 |
| `assets` | 目标项目位置、原模型 checkpoint 或只读发现授权、新数据位置及明确允许的数据用途 |
| `requirements` | 需要保留的能力或明确的“无”，以及业务成功期望 |
| `intake` | 由最小字段缺失固定产生的必答问题、最多 3 个可跳过的选答问题，以及人工确认记录 |

用户原始表述必须保留。模型结构、数据分布、训练入口和方法选择证据不属于初始 `TaskInput`；这些信息由决策 Agent 在任务确认后调用只读工具产生。路径存在性、类型和可读性属于运行环境证据，保存在与当前输入版本及资产声明绑定的独立 `AssetPreflightReport` 中，不写回 `TaskInput`。

字段语义和确认门槛见 [`task-intake.md`](task-intake.md)，可执行结构见 [`../../schemas/task-input.schema.json`](../../schemas/task-input.schema.json)。最小字段缺失时必须形成必答问题；其他补充问题只能是可跳过的选答问题，不得通过猜测或无限制默认值静默补全。

### 6.3 `UpdatePlan`：策略交接契约

必填结构：

| 字段 | 最小内容 |
| --- | --- |
| `plan_version` | 单调递增的计划版本；重规划不得覆盖旧版本 |
| `update_objectives` | 本次更新要达到的目标 |
| `preservation_objectives` | 必须保留的旧能力与容许退化边界 |
| `selected_method` | 选择的方法及适用范围 |
| `rationale` | 选择理由、证据和被排除的重要替代方案 |
| `preconditions` | 执行 Agent 必须在真实项目中核实的前提及验证方式 |
| `constraints` | 数据、资源、修改范围、合规和停止约束 |
| `risks_and_unknowns` | 风险、未知项、影响和处理或升级条件 |
| `validation_strategy` | 小规模验证、正式训练和评估需要证明什么 |
| `acceptance_requirements` | 继承自任务且不可由 Agent 擅自放宽的验收要求 |
| `required_deliverables` | 执行 Agent 必须生成的代码、记录、权重、指标和档案 |
| `replan_triggers` | 哪些证据必须触发重新规划而不是继续实施 |
| `approval` | 计划批准状态、批准人、时间及适用计划版本 |

`UpdatePlan` 不得包含尚未经执行 Agent 核实的项目文件路径、行号、训练入口或 loss 位置。方法级实施要求可以描述，项目级修改方案由执行 Agent 负责。

### 6.4 `ExecutionResult`：执行与交付契约

必填结构：

| 字段 | 最小内容 |
| --- | --- |
| `plan_version_used` | 实际执行所依据的已批准计划版本 |
| `environment` | 代码版本、依赖、设备和影响复现的环境摘要 |
| `precondition_findings` | 每项计划前提的核实结论和证据 |
| `code_changes` | 实际变更摘要及可审阅差异引用 |
| `runs` | 小规模验证、训练和评估的运行编号、配置、命令、时间、退出状态和日志引用 |
| `artifacts` | 新权重、配置及其他产物的位置、类型、大小和完整性摘要 |
| `load_verification` | 加载的新权重身份、使用环境、真实命令、退出状态和结果 |
| `metric_comparison` | 原模型与新模型的指标、数据、评估配置和 checkpoint 对应关系 |
| `plan_deviations` | 相对计划的偏差、理由、影响和批准信息 |
| `failures_and_retries` | 失败、分类、证据、修复和重试关系 |
| `model_record` | 更新后模型描述档案的引用 |
| `unresolved_risks` | 剩余限制、影响和建议处理方式 |
| `execution_outcome` | `completed`、`replan_requested` 或 `failed`，并附理由 |

当 `execution_outcome` 为 `replan_requested` 时，必须引用不成立的前提和原始证据；此时不得伪造完整训练交付。当为 `completed` 时，所有必需产物与验证记录必须存在。

### 6.5 `ReviewResult`：独立审阅契约

必填结构：

| 字段 | 最小内容 |
| --- | --- |
| `reviewed_inputs` | 实际审阅的任务、计划版本、执行结果、代码版本和产物身份 |
| `independence` | 审阅角色身份，以及未参与被审实现的声明或例外 |
| `checks` | 对职责边界、代码差异、命令与退出状态、配置、日志、权重、加载、指标归属、原模型保护和验收项的逐项结论与证据 |
| `reproduced_checks` | 审阅 Agent 实际复验的命令、退出状态和结果；未复验项需说明原因 |
| `findings` | 分级问题、影响、证据和所需动作 |
| `verdict` | `pass`、`pass_with_known_risks`、`changes_required` 或 `invalid_evidence` |
| `acceptance_summary` | 每项任务验收标准是否满足及依据 |
| `required_actions` | 交付前必须修复、重新执行或由人类明确接受的事项 |

`pass_with_known_risks` 只表示证据完整且风险处置符合预先定义的规则，不授权 Agent 放宽验收条件。最终交付决定始终由人类作出。

## 7. 任务状态与转换

最小正常状态流：

```text
任务创建
  → 策略规划
  → 计划待批准
  → 执行准备
  → 小规模验证
  → 正式训练待批准
  → 正式训练
  → 评估
  → 独立审阅
  → 交付待批准
  → 已交付
```

异常状态：

- `重新规划`：计划前提不成立、目标或约束发生实质变化，或评估暴露策略问题；产生新计划版本后返回“计划待批准”。
- `修复后重试`：策略仍成立，但实现、环境或可恢复运行失败；保留失败证据并返回相应低成本阶段。
- `失败终止`：资源、权限、安全、数据或验收问题使任务无法在批准边界内继续；保留所有现有记录和产物清单。

状态转换必须记录时间、发起者、原因、上一个状态、下一个状态和证据引用。不得跳过计划批准、小规模验证、正式训练批准、独立审阅或交付批准。

## 8. 人工批准节点

| 批准节点 | 最小输入 | 人类决定 | 拒绝或退回后的去向 |
| --- | --- | --- | --- |
| 计划批准 | `TaskInput`、版本化 `UpdatePlan`、风险与未知项 | 是否允许执行 Agent 开始项目适配和低成本验证 | 策略规划或失败终止 |
| 正式训练批准 | 小规模验证证据、实际资源估算、已核实前提、训练配置、停止与恢复条件 | 是否允许消耗约定的正式训练资源 | 执行准备、修复后重试、重新规划或失败终止 |
| 交付批准 | `ExecutionResult`、`ReviewResult`、新权重、指标对比、模型档案和剩余风险 | 是否接受并发布本次模型更新 | 修复后重试、重新规划或失败终止 |

任何超出访问边界、修改范围或资源上限的请求都需要单独的人类授权，不能被上述批准隐含覆盖。

## 9. 证据与追溯不变量

1. 原模型身份、计划版本、代码版本、运行编号、新权重和评估结果必须形成可追溯链。
2. 任何失败与重试都保留独立运行编号，不覆盖原始日志。
3. 权重、日志和评估证据在尚未定义保留策略前不得自动删除。
4. Agent 上下文可以只保存摘要，但摘要必须指向完整原始证据。
5. 未知值必须显式表示；不得通过猜测字段、静默降级或默认成功继续。
6. 完成状态必须来自契约校验、真实运行结果、产物检查和独立审阅，而非自然语言总结。

## 10. 后续机械化检查

进入实现阶段后，优先把以下内容转化为机器可读 Schema 和结构测试：

- 四类契约的必填字段、版本和枚举值；
- 状态转换和批准版本的一致性；
- 原权重与新权重路径或内容身份不得相同；
- 每个训练与评估结果必须关联运行编号、配置、数据和 checkpoint；
- `completed` 执行结果必须含权重、完整性信息、加载验证和指标对比；
- `pass` 审阅结果必须覆盖全部强制检查；
- “已交付”必须关联通过的审阅结果和人工交付批准。

检查错误应说明失败项、原因、修复动作和本规格中的权威章节。

## 11. 尚待确定

- 首个小型 PyTorch + EWC 验证项目、数据与量化阈值。
- 契约的具体序列化格式和存储布局。
- 训练隔离、资源配额、超时、取消和恢复的实现。
- 模型档案的完整字段及产物保留期限。
- CLI 原型之后的自动编排方式。
- 更新感知的判据和进入时机。
