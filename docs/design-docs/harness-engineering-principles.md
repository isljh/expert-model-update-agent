# Harness Engineering 原则及本项目应用

## 文档状态

- **状态：** 已确认的设计原则
- **适用范围：** 本智能体系统的仓库组织、Agent 设计、工具设计、运行环境、验证和长期维护
- **参考来源：** [deusyu/harness-engineering](https://github.com/deusyu/harness-engineering)
- **说明：** 本文提炼参考资料中的原则，并结合本项目目标解释其含义。参考资料中的目录、技术和数值是示例，除非本文明确写为本项目约束，否则不直接照搬。

## 1. 总纲：人类掌舵，智能体执行

人类时间是稀缺资源。人类负责定义目标、边界、资源约束和验收标准；Agent 负责完成阅读、规划、修改、运行、评估、审查和修复。

当 Agent 出错时，不应只要求它“更认真”。应判断系统缺少的是上下文、工具、约束、反馈还是可观测性，并把解决办法沉淀进仓库和 harness，使后续任务共同受益。

本项目中的分工是：

- 人类定义模型更新目标、允许使用的数据与资源、必须保留的能力及交付标准。
- 更新决策 Agent 选择更新策略，说明理由、前提和约束，产出 `UpdatePlan`。
- 更新执行 Agent 阅读具体目标项目，核对计划前提，修改代码，实际训练并完成评估。
- Harness 提供仓库上下文、工具、隔离环境、状态记录、可观测性、自动检查和失败恢复。
- 最终交付物包含更新后的模型权重 \(f_{\theta'}\)、评估指标、训练与配置记录以及模型描述档案。

人类掌舵不等于逐步遥控。文件定位、项目适配、错误修复和训练重试等实施细节应由 Agent 在既定边界内自主完成。

## 2. 仓库即记录系统

Agent 运行时无法访问的信息，对它来说等同于不存在。项目目标、架构决策、工具约束和正式验证规则应进入工作区，而不是只留在聊天、在线文档或成员记忆中。构建者的测试题和参考答案则必须与被测 Agent 隔离，不能因为“仓库即记录系统”而进入运行上下文。

本项目需要区分三类空间：

1. **Pi 智能体工作区：** 保存正式运行所需的系统代码、架构、Agent 职责、Skill、Schema、工具接口、建设执行计划和公开验收规则。
2. **构建者记录区：** 位于 Pi 工作区之外，保存测试案例、预期结果、测试对话和隐藏评估记录，不向被测 Agent 提供。
3. **目标模型项目仓库：** 由更新执行 Agent 在一次具体任务中读取和修改。

当前首先建设的是智能体系统仓库。具体目标模型和数据集将在系统验证阶段选择。

建议随着实际内容逐步形成以下结构，而不是预先创建全部空目录：

```text
AGENTS.md   # Agent 入口地图和全局边界
README.md    # 项目定位、状态和文档导航
docs/     # 智能体正式设计与运行规范
├── architecture.md    # 系统架构基线
├── design-docs/     #设计决策，带验证状态
├── product-specs/     # 产品规格和业务契约
├── exec-plans/   # 执行计划、进度和决策日志
│   ├── active/   # 正在进行的建设计划
│   └── completed/    # 已完成计划，需要时再创建
├── references/   # 外部技术或框架参考
└── evaluations/   # 可向 Agent 公开的验收规则，需要时再创建
```

`docs/exec-plans/` 记录构建本智能体系统的工作计划；隐藏评估材料在工作区之外维护。系统运行时由决策 Agent 产生的 `UpdatePlan` 是一次模型更新任务的正式交接物，两者不能混淆。

影响 Agent 行为的重要目标、设计决定、约束和建设进度必须进入 Pi 工作区。构建者的测试题、参考答案和隐藏评估记录不能进入运行上下文；任务数量和并发增加后，可在构建者侧评估 GitHub Issues、Linear、Jira 等任务跟踪器。

## 3. 地图而非手册

`AGENTS.md` 是入口地图，不是百科全书。它只应包含：

- 项目目标的简短说明；
- 权威文档的导航；
- 所有任务都必须遵守的少量边界；
- 当前阶段和重要状态。

方法原理、接口字段、训练规范和评估规则应放在各自的专题文档中。Agent 根据当前角色和任务逐步加载所需内容，避免一次把全部仓库知识塞入上下文。

“约 100 行”或“控制在 60 行内”都是经验值。共同目标是保持入口短小，使 Agent 能快速找到权威信息。具体行数不是业务正确性的替代品。

本项目的渐进式阅读路径应大致为：

```text
AGENTS.md
  ├─ 项目定位与状态 → README.md
  ├─ 系统职责与流程 → docs/architecture.md
  ├─ 设计理由 → docs/design-docs/
  ├─ 当前工作 → docs/exec-plans/active/
  └─ 验收方法 → docs/evaluations/
```

## 4. 机械化执行

已经明确且可以客观判断的要求，不应只写成提醒，还应逐步编码为 Schema、lint、结构测试、运行检查或 CI 门槛。

机械化执行约束的是不变量，不微观管理 Agent 的实施过程。例如，不预先规定 EWC 必须修改哪个文件或哪一行，但可以强制：

- 原模型权重不得被覆盖；
- `UpdatePlan` 必须包含执行所需的关键内容；
- 每次训练必须关联代码版本、配置和运行编号；
- 训练失败不能标记为成功；
- 模型更新完成必须存在可加载的新权重和评估结果；
- 原模型和新模型的指标必须注明对应数据与 checkpoint；
- 交付产物之间必须可以相互追溯。

错误信息应同时说明问题、修复动作和权威文档位置，使 Agent 能够形成自我纠正闭环：

```text
Agent 实施
  → 自动检查
  → 返回可执行的错误说明
  → Agent 修复
  → 重新检查
```

自动检查适合确认文件、格式、依赖方向、退出状态、权重可加载性和明确数值门槛。它不能独立判断策略是否科学合理、算法实现是否真正正确或实验结论是否具有研究意义；这些仍需独立评估和审查。

参考资料中的具体分层顺序和 lint 规则属于原项目示例。本项目应在架构确定后定义自己的依赖方向和不变量。

## 5. 智能体可读性

优化目标不仅是“人能读懂”，还包括 Agent 能在有限上下文中理解、操作、观察和修复系统。

### 5.1 选择稳定且常见的技术

优先采用 API 稳定、文档充分、行为显式、错误容易定位且模型训练语料覆盖充分的技术。第一版宜使用常见项目结构、清晰命令行入口、结构化配置和明确的输入输出。

LangGraph、A2A、MCP、Pi 等都是候选技术或协议，不能仅因架构图或文章出现就预设为必选。应根据实际需要判断它们是否提高了可理解性、可操作性和可靠性。

### 5.2 必要时实现透明的关键子集

当第三方上游行为不透明，而本项目只需要范围很小、能够充分测试的功能子集时，可以考虑自行实现。自有实现必须具有明确输入输出、可预测行为、充分测试和统一可观测性。不能把“自研”本身当成目标，也不应重复实现成熟训练框架或基础设施。

### 5.3 控制上下文腐化

- **阶段压缩：** 将已完成探索压缩为结构化结论、证据位置和未完成项。
- **工具输出卸载：** 完整训练日志和大型输出保存到文件，Agent 上下文只保留摘要、关键错误和路径。
- **渐进式披露：** 按角色和当前方法加载文档与工具。例如只有选定 EWC 后，执行 Agent 才加载 EWC 的详细能力。

压缩不能丢失目标、约束、关键决策、证据位置和未解决问题。

### 5.4 让系统可以被 Agent 操作和观察

对于本项目，Agent 应逐步获得以下能力：

- 在隔离工作区读取和修改目标项目；
- 启动、停止并重新运行训练和评估；
- 观察进度、损失、指标、错误和资源使用；
- 检查 checkpoint 是否生成并能否加载；
- 将代码版本、配置、日志、权重和指标关联到同一次运行。

`git worktree` 可用于隔离代码修改，但不能自动隔离数据、Python 环境、日志路径、checkpoint 和 GPU。完整隔离单位应是带唯一编号的“模型更新运行”。

原文中的 Chrome DevTools、LogQL 和 PromQL 是 Web 服务场景的实现示例。本项目应选择适合机器学习训练的观测方式，不直接照搬。

### 5.5 约束提高自主性

明确的边界可以缩小错误解空间，使 Agent 在边界内更可靠地自主行动。约束应集中在数据权限、原模型保护、评估完整性、交付条件、资源上限和失败处理，不应把项目级实施步骤全部写死。

## 6. 吞吐量改变合并理念

当 Agent 的产出速度超过人类注意力时，工作单位应从单个 PR 提升到完整任务。人类提交并验收任务，编排器负责中间的拆分、PR、审查、CI 重跑和修复。

在本项目中，更自然的工作单位是一次模型更新任务：

```text
更新任务
  → UpdatePlan
  → 隔离实施
  → 一个或多个代码修改
  → 小规模验证
  → 一次或多次训练与评估
  → Agent 审查和修复
  → 最终 review packet
```

审查 Agent 应独立核对代码和真实产物，而不是只阅读实施 Agent 的总结。长时间任务可以采用类似 Ralph Loop 的机制，在新上下文中重新注入原始目标和持久化状态，直到满足完成条件或触发停止条件。

快速流动必须建立在测试、lint、结构检查、可观测性和回滚能力之上。已确认的偶发性、非关键环境失败可以自动重试；稳定复现的失败、架构违规、训练错误、不可加载权重和不可信指标不得通过重复运行绕过。

模型训练的纠错成本可能很高，因此应区分：

- **低成本迭代：** 分析、规划、代码修改、静态检查和小规模试运行，可以快速循环。
- **高成本阶段：** 正式训练、完整评估和模型交付，需要更严格的进入条件与交付门槛。

最终 review packet 应聚合任务、计划、代码差异、训练配置、日志摘要、原模型与新模型指标、新权重信息、检查结果和未解决风险，让人类审查证据而不是跟踪所有中间动作。

## 7. 熵管理与垃圾回收

Agent 会模仿仓库中已有的模式，包括坏模式。重复工具、不一致状态、未经校验的数据结构、过时文档和无法追溯的训练产物会被后续 Agent 继续复制，因此技术债会加速扩散。

应把反复出现并已形成共识的问题转化为“黄金规则”：

```text
审查发现问题
  → 更新设计文档
  → 编码为 Schema、lint 或测试
  → 自动作用于后续代码
  → 定期扫描历史偏差
```

本项目可能形成的黄金规则包括：

- 统一模型更新运行记录、状态和产物清单；
- 统一 checkpoint 元数据和评估结果结构；
- 外部数据和工具输出在边界处校验，禁止通过猜测字段并静默降级；
- 原始模型只读；
- 共享能力集中实现，不在不同方法工具中重复复制；
- 文档状态必须与代码和实际产物一致。

“禁止 YOLO 探测”不等于禁止执行 Agent 探索陌生项目。Agent 可以提出和验证假设，但不得把未经确认的猜测作为正式接口并在错误时静默继续。

定期垃圾回收可扫描失效链接、过时文档、长期未完成计划、重复实现、绕过公共能力的代码、未校验输入及无法追溯的产物，并通过小型修复持续偿还技术债。

模型权重、训练日志和评估记录可能是实验复现证据，不能被后台任务随意删除。未来必须先定义产物分类和保留策略，再自动清理明确标记、可重新生成且超过保留期的临时文件。

## 8. 六项原则如何共同工作

```text
人类定义目标、边界和验收标准
              ↓
仓库记录系统提供可信上下文
              ↓
入口地图与渐进式披露控制上下文
              ↓
可读、可操作、可观察的环境支持 Agent 执行
              ↓
机械化检查提供快速反馈和不可绕过的底线
              ↓
高吞吐循环完成实施、审查、修复和交付
              ↓
熵管理把新经验转化为长期规则
```

这些原则共同服务于一个目标：让 Agent 获得足够的执行自主性，同时让每次模型更新具有明确边界、真实运行结果和可验证证据。

## 9. 后续构建时必须遵守的决策准则

1. 重要事实、决定和状态进入仓库，不能只存在于对话中。
2. `AGENTS.md` 保持为短入口，详细知识放入专题文档。
3. 不机械复制参考仓库的完整目录和具体技术；目录随真实内容增长。
4. 每确定一个重要约束，都判断它能否转化为自动检查以及错误信息能否指导 Agent 修复。
5. 决策 Agent 负责“选什么方法、为什么”；执行 Agent 负责“在具体项目中怎样实现、训练和评估”。
6. 工具提供可信事实、算法组件和验证能力，不承担项目级自主判断。
7. 第一版优先选择稳定、透明、常见、可调试的实现，避免无必要的复杂编排和协议。
8. 大型日志和中间产物保存在上下文之外，但必须可追溯和按需读取。
9. Agent 可以快速迭代低风险修改；正式训练和模型交付必须通过严格验证。
10. 只有实际训练产生新权重，且评估结果与证据齐全，才可声明交付 \(f_{\theta'}\)。
11. 发现重复错误时，优先改进仓库上下文、工具、约束或反馈回路，而不是只增加提示语气。
12. 通过持续的小型清理控制熵；未经明确保留策略，不自动删除训练与模型证据。
